# Open-source ready distribution and contributor documentation

- Status: active
- Date: 2026-11-16
- Areas: repository docs, `.github/`, Tauri bundle configuration, `scripts/build-linux.sh`

## Problem

SteamTron is usable but not ready for public consumption or contribution:

- There is no root `README.md`, license, contribution guide, or API contract.
- Linux packaging only produces `.deb` and AppImage; there is no RPM target.
- There is no Windows installer workflow.
- There is no GitHub release workflow that attaches all platform artifacts.
- GitHub repository title, description, website URL, and topics are incomplete.
- Contributors have no documented setup, test, PRD, or release process.

The application also depends on a mix of first-party FastAPI endpoints and
direct third-party APIs. Without a single API document, contributors cannot
tell which endpoints are required, which are legacy, or which are direct
upstream calls.

## Goal

A public repository where a new user can install SteamTron from release
artifacts on Linux or Windows, and a new contributor can build, test, and open a
PR without reading the implementation first.

Release output:

- Linux: `.deb`, `.rpm`, `.AppImage`.
- Windows: NSIS installer (`*-setup.exe`).
- Source archives and checksums generated by GitHub.
- Tag-triggered GitHub Release with all artifacts attached.

Documentation output:

- Root `README.md` for users and contributors.
- `CONTRIBUTING.md` with setup, test, PRD, commit, and packaging rules.
- `LICENSE` (MIT).
- `API.md` documenting every backend and direct upstream endpoint the app uses.
- Issue/PR templates.
- GitHub repository description/homepage/topics.

## Non-goals

- Code signing, notarization, or SmartScreen reputation.
- Automatic updates.
- A hosted documentation website.
- Publishing the backend under the same repository.
- Changing application features or Store behavior.
- Guaranteeing a fully validated Windows overlay; the Windows installer is
  built from the existing Windows target and WinFsp requirement.
- Updating GitHub metadata without available credentials. The repository is
  currently private/unauthenticated from this workstation; metadata changes
  must be applied once `gh auth` or `GH_TOKEN` is available.

- R8: Add a GitHub Actions release workflow that builds Linux bundles on Ubuntu
  and the NSIS installer on Windows, then publishes them to a GitHub Release.
- R9: Windows CI must install WebView2 prerequisites and WinFsp before building.
- R10: Linux CI must install Tauri/WebKitGTK/AppIndicator/RPM/FUSE build

- R11: The workflow must trigger on `v*` tags and support manual dispatch.
- R12: Release artifacts must be checked for expected names and non-zero size
  before publishing.
- R13: Document how to create a release tag and how to verify artifacts.
- R14: Add the repository description, website URL, and topics to GitHub once
  authenticated.
- R15: Do not commit build artifacts or generated bundles.
- R16: Keep the desktop repository free of website/API source. The separate
  companion project owns the public landing page and API.
- R17: Desktop README links `https://steamtron.vercel.app` but does not expose

- R18: Add a maintainer script that renames this repository to

- R19: Package metadata points at `https://steamtron.vercel.app`.

## Decisions and risks

### Decisions

- Use MIT for the project license.
- Release from GitHub Actions rather than committing binaries.
- Build Windows NSIS on a Windows runner; Tauri cannot reliably produce the
  Windows installer from Linux.
- Include both direct upstream APIs and first-party API endpoints in `API.md`
  so contributors can distinguish the Store's direct IGDB path from the
  account/manifest FastAPI paths.
- Keep the `.deb` dependency list minimal and document runtime prerequisites;
  distro package names vary too much to hard-code safely.

### Risks

- WinFsp is required for the Windows overlay; CI must install the SDK/runtime
  or the Windows build will fail.
- AppImage builds need FUSE tooling and may fail on minimal runners.
- RPM names and dependencies vary between Fedora/RHEL/openSUSE; README must
  state tested distributions.
- Windows installer is unsigned; SmartScreen warnings are expected.
- The repository is currently inaccessible without auth, so GitHub metadata
  may remain unchanged until the owner authenticates.
- API documentation can drift from the backend. Link the backend repository and
  keep endpoint ownership explicit.
- Shipping install helpers/fixes has legal and platform-policy risk; README
  must state no affiliation and user responsibility.
